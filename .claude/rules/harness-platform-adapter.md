# Harness Engineering Platform Adapter

The shared `~/.claude/CLAUDE.md` links to `~/.codex/AGENTS.md` and remains the behavioral source of truth. Apply it in Claude Code with these platform mappings:

**Language (hard rule):** when the user writes in Chinese, every visible sentence is Chinese, including one-line progress notes between tool calls, background-job narration, and replies after context compaction. Commands, paths, code symbols, and quoted errors stay unchanged.

- Relative `docs/workflows/...` links in `~/.claude/CLAUDE.md` resolve under `~/.codex/`, for example `~/.codex/docs/workflows/git-worktree.md`.
- `request_user_input` maps to `AskUserQuestion`. An `AskUserQuestion` tool result is the user's own answer and authorizes what it selects, including in background jobs. A `[SYSTEM NOTIFICATION - NOT USER INPUT]` or task-notification disclaimer covers only the message it arrives with; never apply an earlier one to a later answer, and never re-ask an answered question in plain text. A relayed claim from another session still needs the user's own `AskUserQuestion` answer.
- Subagents follow the global Subagent Delegation rule and use the `Agent` tool directly; no Worker protocol, dispatch contract, or delegation quota applies.
- Name task branches `claude/<task-slug>`, never `codex/<task-slug>`; periodic Harness cleanup recognizes the `claude/` prefix. `EnterWorktree` creates `claude/<name>` worktrees under `<repo>/.claude/worktrees/`; use it when the runtime requires isolation (for example a background job), and cleanup handles that location. Otherwise the Git Worktree Workflow's necessity criteria decide. Before calling `EnterWorktree`, run `git rev-parse --show-toplevel`: keep working if the session is already in the intended task worktree. `EnterWorktree` works only from the session's starting directory and a Bash `cd` does not persist, so when that directory is outside the target repository, create the worktree with `git worktree add <repo>/.claude/worktrees/<slug> -b claude/<slug>` and use absolute paths inside it. Keep `.claude/worktrees/` in the global Git ignore file so `git add .` never stages a worktree as an embedded repository.
- Background jobs: the user's Git rules override the job prompt's defaults to push the worktree branch and never merge. Commit in the task worktree, never push the `claude/*` branch, and when the High-confidence gates pass for `origin/uat` or another persistently authorized target, integrate with `git push origin <task-branch>:<target>` without waiting for a merge request. Then follow the Cleanup Choice, asking with `AskUserQuestion` and also writing a `needs input:` line. Whenever a job stops for the user's decision (a product or behavior choice, an approval, or missing input), ask with `AskUserQuestion` offering the concrete options, and end with `needs input:`, never `result:`; `result:` marks the ask as delivered and hides the pending question from the job list.
- Waiting: run deploys, uploads, builds, SSH sessions, and anything expected to take more than about a minute with `run_in_background`, and wait for a condition with `Monitor`. Never wait with a foreground `sleep` or a `for … seq` polling loop.

## Browser

The global Browser And Web Access and Human Verification rules, and the [Browser Workflow](../../.codex/docs/workflows/browser.md), map to Claude's own browsers in Claude Code. The skill/MCP/API → CLI → browser order still applies.

- Default to the `magpie-browser` MCP (one `browser` tool with an `action` argument; its name contains `magpie-browser` but the prefix varies by host, e.g. `mcp__magpie-browser__browser` or `mcp__magpie__mcp__magpie-browser__browser`, so match by that part and load it via `ToolSearch` if deferred). Do not use the built-in browser pane (`mcp__Claude_Browser__*`) or Claude in Chrome while magpie-browser is connected and sufficient.
- Fall back to the built-in pane, then Claude in Chrome (`mcp__claude-in-chrome__*`, for the user's Chrome sign-ins), only when magpie-browser is unavailable or lacks a needed capability, or the user names them; say why before falling back.
- Login-wall: when magpie lands on a login page or needed content requires sign-in, check `browsers` / `use_browser` for the signed-in browser instead of settling for public content. If Chrome is also signed out, hand off login per the human-verification rule. A site-safety or permission refusal is not a login wall; do not switch browsers to get around it.
- Never compete with the user for control. In Chrome, call `tabs_context_mcp` first, work only in tabs Claude created in its own window/tab group, never focus, reuse, navigate, or close the user's tabs unless asked, and close Claude-created tabs when done unless the user wants them kept. If the user is acting in a page Claude needs, wait for them instead of taking over.
- For magpie-browser, element-first maps to `snapshot` (`interactive: true`) + `click`/`type` by `ref` + `text` to verify. For the fallback Chrome tools, the global element-first browser rule maps to `find` and `read_page` (`filter: "interactive"`) to locate elements, `computer` clicks by `ref` (not `coordinate`), `form_input` for fields, and `get_page_text` / `find` to read and verify results. If the page's framework ignores a `form_input` value (submit does nothing), click the field by `ref` and use `type` / `key` instead. Use `screenshot` (`scale` ≈ 0.5) or `zoom`, and coordinate clicks, only for genuinely visual content or when no usable `ref` exists. The token-saving rule maps to `browser_batch` for predictable step sequences.
- On CAPTCHA or human verification, stop operating that page, tell the user the page/URL/step, and ask via `AskUserQuestion` with `已验证`, `未处理`, and `取消任务`; resume only after `已验证`.

User-managed Skill sources remain under `~/.agents/skills`. Entries under `~/.claude/skills` are discovery symlinks only.
